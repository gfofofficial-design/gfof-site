# Helius intake preparation — no live route

Reviewed against the official [webhook overview](https://www.helius.dev/docs/webhooks), [FAQ](https://www.helius.dev/docs/faqs/webhooks) and [migration guide](https://www.helius.dev/docs/parsed-events/guides/migrate-from-enhanced-transactions) on October 13, 2026.

Helius echoes the configured authorization value in the Authorization header. Its FAQ says deliveries occur after confirmation, duplicates may occur, successful receipt should return HTTP 200 within one second, and retries are bounded with permanent loss possible. Current overview pricing charges credits for delivery even if processing fails. A header match is a shared-value check, not a signed payload, independent finality verification or proof of a transaction's meaning. Anyone holding that value can forge or replay a request.

The prepared server core requires explicit enablement, an injected Bearer value in a bounded base64url format, an explicit account watchlist and a reviewed receipt-acceptance callback. It checks the header with fixed-size SHA-256 hashes and timingSafeEqual before consuming the body. It refuses unsupported content encoding/type and caps actual body reads at 256 KiB. The whole read/parse/acceptance operation has a maximum 750 ms deadline. Success is returned only when the callback returns exactly true before that deadline. Late storage completion is possible and must be handled idempotently by the future sink; a timeout never returns success. No callback/database is provisioned here.

Only enhanced-webhook signature, slot and accountData account membership are projected into candidate receipts. Up to 100 transaction entries and 256 account entries per transaction are accepted. Conflicting duplicate signatures refuse the delivery; duplicates within the delivery are counted. Type labels, amounts, description, metadata, user details and raw provider errors are not retained or returned. Unwatched transactions are counted but not enqueued as candidates. Receipts require independent finality and state verification: they are not transfers, sales, authority changes or lock-schedule findings. Native/enhanced metadata is not trusted to establish those classifications.

This is a server-only module under _shared: no HTTP handler, route configuration, environment lookup, webhook creation, new credential, live subscription, paid provider call, alert or deployment is activated. Mainnet binding is a future trusted webhook/deployment configuration requirement; a payload/header match does not independently establish its network.

Before activation: independently review the exact watchlist and provider plan/credit budget; compare webhook support with the newer Parsed Streams option recommended for new builds by current Helius docs; select an authenticated durable sink with signature-based idempotency across deliveries; prove receipt/retry/recovery under the provider acknowledgement deadline; add bounded independent finality/state verification and backfill; review retention and operational monitoring; obtain separate activation authorization. Enhanced REST migration guidance leaves enhanced webhook payload handling unchanged; no existing integration is migrated by this draft.
