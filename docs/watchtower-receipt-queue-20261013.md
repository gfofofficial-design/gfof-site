# Durable candidate receipts — review only

The prepared receipt sink projects and validates candidate signature, slot and canonical matched accounts, then calls a parameterized PostgreSQL enqueue function. Success requires committed acceptance for the entire candidate list. Aborted or failed writes return false. An empty list is accepted without adding queue rows. A late commit after the HTTP deadline is possible; retries must be idempotent and never imply a second event.

The migration is for isolated acceptance only. It has not been applied to a live database. Mainnet candidate signatures are unique across deliveries. Identical repeats preserve one row and never reopen processed work. Conflicting slot/account content aborts the entire enqueue statement, including any new rows earlier in that batch. Sorted locking reduces reversed-batch deadlocks. A watchlist change may alter matched accounts and require explicit reconciliation; do not silently rewrite evidence.

Workers claim one item with FOR UPDATE SKIP LOCKED, a thirty-second lease and an incrementing lease version. Expired leases can be reclaimed. An expired or older-version worker cannot finish a newer lease. Five claims exhaust the candidate and leave it visible for investigation instead of retrying forever. Processed means queue processing finished; it does not independently prove finality, transfer meaning, source authenticity or monitoring completeness. No worker, RPC verification, emitted finding or notification is activated here.

The disposable PostgreSQL CI service tests twenty simultaneous identical receipts, full conflict rollback, ten simultaneous claims, lease expiry/recovery, stale-worker rejection, processed receipt replay and bounded exhaustion. It uses fixed fixture credentials, no cloud secrets or live database URLs, and no package installation. Local mock tests are not concurrency proof; final-head isolated acceptance must pass.

Before production: owner-approved storage/retention, reviewed backup and migration, TLS-verified server connections, a database statement/lock deadline that fits the sub-second intake budget, narrowly granted enqueue/worker roles and bounded independent verification. Functions use invoker privileges and PUBLIC privileges are revoked; no service roles are created or granted. Server role/table permissions must be reviewed for the selected database; do not expose this table to browser clients. Authenticated receipt provenance, recovery/backfill after provider loss and transactional downstream output still need separate implementation and proof.
