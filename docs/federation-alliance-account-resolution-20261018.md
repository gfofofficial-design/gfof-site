# Alliance conditional account reconciliation candidate

October 18, 2026. Disabled local source; no hosted setup, public route or automatic
reconciliation service. Existing SQL and credentials are unchanged.

## What can be established

A lost reply does not show whether the original caller committed. This candidate
does not attempt that attribution. It can settle a narrower question using the
complete canonical account history and monotonic acknowledgement:

| Original request | Resolvable condition | Recorded outcome |
| --- | --- | --- |
| Append an exact event at an expected tip | The exact event appears later in the canonical chain | `effect_satisfied` |
| Append an exact event at an expected tip | Event absent, but a different successor permanently displaced that tip | `superseded` |
| Advance an acknowledgement from an expected prefix to a target | Current acknowledgement is at or beyond that exact canonical target | `effect_satisfied` |
| Advance an acknowledgement from an expected prefix to a target | Current acknowledgement advanced beyond expected, but remains below target | `superseded` |

Absence with an unchanged expected point remains pending. A transport timeout,
negative reply, elapsed time or operator-supplied success flag cannot resolve it.
An exact no-op acknowledgement is an already satisfied effect; it proves no caller
commit. A matching event committed by a different writer is likewise an observed
effect, not proof of which request executed.

## Why a late original request cannot change these conditions

This reasoning is specific to the reviewed `alliance_account` store contract.
History is append-only under the normal writer role, each canonical event is
unique, admission cannot repeat after removal, and a new append must match the
current expected sequence AND hash. Replaying an existing event cannot append it
again. An absent event with a displaced expected tip cannot be appended by the
original immutable request. Acknowledgement advance similarly requires its exact
expected current point and never lowers the prefix.

The original SQL locks its control row before reading the current tip and testing
these conditions. A request waiting for that row must observe the subsequent
committed state or fail. See [PostgreSQL row locking](https://www.postgresql.org/docs/17/explicit-locking.html)
and [transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html).
The unchanged SQL candidates are `alliance-account-history-store-candidate.sql`
and `alliance-account-ack-store-candidate.sql`; generic storage providers or changed
function bodies do not inherit this proof.

The [installed-contract verification candidate](federation-alliance-account-contract-20261018.md)
now checks the full reviewed function closure and narrow protections before
dispatch and in a fresh catalogue snapshot after COMMIT. It detects persistent
drift, while privileged-DDL races, restores and old-producer fencing remain gated.

This is not global fleet fencing. Privileged history rewrites/restores, old servers
with different mutation rules, changed SQL, non-conditional transports and other
side effects invalidate these assumptions. Installed-definition/privilege checks,
restore barriers and old-producer fencing remain production acceptance gates.
The scope is the account-store mutation only, not multi-step Auth provisioning,
profile/image deletion, wallet activity or physical erasure.

## Separate reviewer and explicit opt-in

`account-resolution.mjs` derives the condition from complete canonical history
extending both protected minima. It checks the original expected/target hashes in
that same chain and refuses an append event that predates its staged request.
`reviewAccountResolutionSuccessor` is a different entry point from ordinary
handoff successor review. A supplied receipt cannot bypass independent derivation.

The coordinator's new `reconcile()` method requires `reconciliationEnabled: true`
in addition to the existing `enabled: true`; both default false. It loads the
current protected pair, checkpoints any newer observations, derives the condition,
then conditionally commits the resolution record and outside receipt and reads
both back. It never calls `history.append` or `acknowledgements.advance`.
Ordinary `execute` still refuses pending work; no mutation retry or new ID is
generated by reconciliation.

Partial commits remain closed. If the record commits but the outside receipt does
not, restart refuses the mismatched pair without repair. If both commit but their
reply is lost, the original instance returns unknown; a fresh instance can read
the settled state independently. Cancellation, close or uncertain storage faults
the instance; late completion cannot turn its abandoned response into success.

## Versioned retained evidence

Format1 canonical bytes remain unchanged. Only successful resolution can upgrade
a pending record to format2, clear its pending field and retain a canonical
`resolution` containing the original full intent, prior checkpoint digest, outcome,
observed head/ack and causal guard point. Ordinary successors cannot perform that
upgrade, clear pending, change the retained receipt or downgrade format2 to1.

Future observations and new staged operations preserve the last receipt. A later
verified resolution replaces it with its own causally linked receipt. This is
bounded latest evidence, not an immutable archive of every operation. Backend
history retention and coordinated recovery of checkpoint records/receipts remain
unimplemented. IDs are interpreted with checkpoint digest/scope/generation; this
does not establish globally unique caller identities or an exactly-once workflow.

Neither outcome establishes authorization, current admission, safety, erasure or
instant cross-database revocation. An admission effect can be present while that
same account is already removed; fresh account/session/policy/content checks are
still required on every operation.

## Verification and release limits

Pure and coordinator tests cover all four conditions, unchanged-tip pending,
complete-chain/pin refusal, fabricated receipts, v1/v2 boundaries, successor
restrictions, no business writes, storage conflicts/lost replies/close and later
operations preserving/replacing the last receipt. Real disposable SQLite tests
verify settled close/reopen and a split commit remaining closed; SQLite stays
test-only and provides no independent real custody proof.

The disposable native TLS driver also uses the actual PostgreSQL history/ack
adapters with deliberately lost mutation COMMIT replies. It verifies late append
idempotence, late acknowledgement conflict, unchanged-point pending, displaced
append rejection and intermediate acknowledgement supersession. Only exact new
synthetic rows/points are removed to restore the surrounding fixture baseline.
Its checkpoint capabilities are in memory, not a hosted durability acceptance.

No SQL, hosted permission, new dependency, real key, provider RPC, purchase,
public-site change or background service is introduced. Production protected
backend/current receipt custody, installed contract and old-producer/restore
barriers, key provenance, managed/coordinated recovery and per-operation runtime
integration remain before a release decision.

## Accessibility and privacy

No interface changes. Future plain text should distinguish “recorded effect
confirmed,” “original request can no longer change this history,” and “still
pending; not retried.” Do not translate superseded into a claim that nothing ever
committed. Use persistent status, keyboard/screen-reader controls and support after
sign-out; no countdown, secret re-entry or hash transcription. These backend tests
are not WCAG conformance evidence. Retained account tags/operation IDs can be
linkable; real access, retention and deletion policy remains a release gate.
