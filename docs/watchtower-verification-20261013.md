# Candidate corroboration — disabled server core

Reviewed against Solana's [getTransaction](https://solana.com/docs/rpc/http/gettransaction) and [getMultipleAccounts](https://solana.com/docs/rpc/http/getmultipleaccounts) references on October 13, 2026.

The injected verifier requests one transaction at finalized commitment with JSON encoding and maximum supported transaction version zero. It requires the queried signature as the first transaction signature, the queued slot, successful metadata, and every watched candidate account in the returned static or loaded account keys. Null, failed, unsupported, mismatched or incomplete transactions stop before the account lookup.

The next reserved request reads the candidate accounts at finalized commitment with minContextSlot equal to the transaction slot. Response count/order and context slot must match the request constraints. Existing accounts receive an owner-program label, executable flag, byte length and canonical data/state SHA-256 fingerprints. A null account remains explicitly absent at the account-read slot. These are current snapshots, not reconstructed transaction-time state. No lamport/token amount, transfer, sale, beneficial-owner, control change, lock effect or safety finding is inferred.

This core is disabled by default. Enabling requires an explicit copied watchlist, a reviewed mainnet RPC callback and a durable allowance callback. Each of the at-most-two reads reserves one request before RPC work. The total deadline is at most eight seconds; there are no retries or refunds. Cancellation-ignoring callbacks time out without later success. Malformed RPC IDs/errors/results are refused, response JSON is bounded to one MiB and account data to 32 KiB each. The future transport must also enforce the raw byte limit while reading, authenticate TLS and bind the reviewed endpoint to mainnet; injected decoded JSON is not a transport implementation.

No RPC endpoint, key, environment lookup, provider call, durable allowance, worker or alert is activated. Tests use synthetic JSON-RPC responses only. The returned source label explicitly says the RPC response is not cryptographically verified: callback provenance must be established by a real reviewed transport, and multiple reads are not atomic. This is not a comparison of independent providers or a proof of consensus. The core never automatically promotes these results into the offline replay's reported transfer/control/lock categories.

Next gates: reviewed provider/network transport and allowance, integration into lease processing, durable retention of corroboration plus transactional processing completion, explicit retry versus exhausted/review outcomes, historical baseline and program-specific decoding before any claimed change, backfill/recovery tests, owner-approved watch scope/cost and separate live activation. Account fingerprints alone do not explain why a state changed.
